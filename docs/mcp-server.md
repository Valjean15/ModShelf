# The MCP server

`mcp` runs an [MCP](https://modelcontextprotocol.io) server on standard input and output, which an agent's app, such as Claude Desktop or Claude Code, starts and talks to. Through it, an agent can see the library, its updates, the downloads and the settings, and act on them, such as when it helps you keep a mod manager's mods up to date: ModShelf downloads the files and keeps their versions, and the mod manager installs them. ModShelf never installs mods.

## Turning agents on

**Agents are off until you turn them on**: Settings › **Agents**, **Allow agents to use ModShelf** (`agents.enabled`). While they're off, the server still starts and lists its tools, and answers every call saying agents are off and where to turn them on; the setting is read at each call, so turning it on needs no restart of the agent's app. An agent can't turn it on or off itself. While they're on and the desktop app runs, it also serves the server at an address, `http://127.0.0.1:47823/mcp` (Streamable HTTP; the port is `agents.port`), for agents' apps that reach servers by address: the command line's `mcp --http`, which the app runs beside it and ends when it quits, answering this computer's apps alone. On the same page:

- **Copy prompt** puts on the clipboard a prompt to paste into the agent's chat: it asks the agent to add the server named `modshelf` to its app's configuration, with this computer's command and the library's settings, or the address where its app reaches servers by address.
- **View details** shows the server's name, command, arguments and environment, the address, the JSON for Claude Desktop and the `claude mcp add` commands for Claude Code, each with **Copy**.
- **Add to Claude Desktop…** adds the server to Claude Desktop's `claude_desktop_config.json`, after asking, keeping its other servers and a copy of the file as it was (`claude_desktop_config.modshelf-backup.json`); then quit Claude Desktop completely and start it again. On Windows, the Microsoft Store's Claude Desktop keeps its file in its package, which ModShelf finds.

## Connecting an agent by hand

For Claude Desktop, add it to `claude_desktop_config.json` (**Settings**, **Developer**, **Edit Config**), with your own user folder, then restart Claude Desktop:

```json
{
  "mcpServers": {
    "modshelf": {
      "command": "C:\\Users\\<you>\\AppData\\Local\\ModShelf.App\\current\\ModShelf.Cli.exe",
      "args": ["mcp"]
    }
  }
}
```

For Claude Code, in PowerShell: `claude mcp add --transport stdio --scope user modshelf -- "$env:LOCALAPPDATA\ModShelf.App\current\ModShelf.Cli.exe" mcp`; or, while the desktop app runs, by its address: `claude mcp add --transport http --scope user modshelf http://127.0.0.1:47823/mcp`. On macOS, the command is `/Applications/ModShelf.app/Contents/MacOS/ModShelf.Cli`. From a build, it's the `ModShelf.Cli` executable in `src/ModShelf.Cli/bin/Debug/net10.0`, not `dotnet run`, which can write the build's output where the protocol goes; a desktop app built from source finds it there too, or where `ModShelf__CommandLine` says. An AppImage's command line moves each time it starts, so on Linux, agents' apps use the address, or the command line of a build. The environment variables the command line takes, such as `ModShelf__DatabasePath`, go in the app's configuration of the server (`"env"` in Claude Desktop's). [ADR 0040](architecture.md#the-mcp-server-and-agents) and [ADR 0080](architecture.md#the-mcp-server-and-agents) have the details, and [manual-checklist-mcp.md](manual-checklist-mcp.md) the checks to make by hand.

## Several `ModShelf.Cli` processes

Several `ModShelf.Cli` processes can run at once, and that's expected: each agent's app starts the command line for itself, once for each MCP server it's set up with, and keeps it running while it runs (Claude Desktop on Windows starts each local server twice, a bug of its own); Claude Code starts one for each session. While agents may use ModShelf, the desktop app runs one more for the address, which ends with the app. Each waits for its agent's calls, and since 1.0.1 none of them can make the app wait for the library database. Each one's log starts with what it runs and the process that started it, such as `Claude`; Task Manager's **Details** tab, or `Get-CimInstance Win32_Process -Filter "Name='ModShelf.Cli.exe'" | Select ProcessId, ParentProcessId, CommandLine` in PowerShell, shows the same.

## Tools

- `library_list`, the mods and their files, with absolute paths, versions, sizes and SHA-256s, whether they're archived old versions, and whether they're missing from disk, a page at a time (50 mods unless `limit` says otherwise), for a game, a site or a mod if asked, watched ones, ones with updates or ones with files missing from disk only (`watchedOnly`, `updatesOnly`, `missingOnly`), or `compact`, with counts in place of files; `library_changes`, the files downloaded since a time, each with the older version it replaced and what became of it (`archived`, `deleted`, `kept`, or `gone` from the library otherwise), and its mod's other files in the library; `library_updates`, the updates found, each with its link, the library file it replaces, and its `kind`, `update` or `newFile` for a file that replaces none, such as a new optional file, and with `changelog`, what changed; `library_check`, which checks the watched mods now; `library_watch` and `library_unwatch`; `library_forget`, which takes a mod out of the library as `library forget` does, its files staying on disk; `library_rescan`, as `library rescan` does; and `library_pin`, `library_skip` and `library_note`, as `library pin`, `library skip` and `library note` do. `library_updates` and `library_check` leave out a pinned mod's updates and the ones skipped, which `library_list` and `mod_show` still give, each saying whether it's skipped, with each mod's `pinned` and `note`.
- `download`, which downloads files' or mods' links into the library, as the desktop app does: from 1 to 50 links in `links`, in the order given (`link`, one link as `download` took before 0.9.3, still works until ModShelf 2.0 but is deprecated; see below), each with its own result, so one that can't be downloaded says why and the others go on, and each download as it is when the call ends, such as downloaded already or failed; `downloads_list`; and `downloads_pause`, `downloads_resume`, `downloads_retry` and `downloads_cancel`, by a download's ID or its first 8 characters; `downloads_take` hands a download waiting on a site's page the file the browser downloaded, by its full path, checked and moved into the library as the desktop app's **Choose the file…** does.
- `mod_games`, as `mod games` does, a page at a time, and with `installed` the games Steam installed on this computer, each with its games on the sites (`stores`, `installed`, and `problems` for a site that couldn't list its games); `mod_show` and `mod_search`, as `mod show` and `mod search` do, `mod_search` with `category` and `updatedWithin` too, how many mods with adult content a page left out (`leftOut`), and with what the site's search can do for the game in each result's `search`: its orders and which ways round, the filters it takes, its largest page, its word for approval, and the game's categories; `mod_show` with where the library has each file, the newer file that replaces it (Nexus Mods lists some links back in time, to a file uploaded before, which are left out), and, in `libraryOnly`, the library's files the site no longer lists, such as a pulled file; `settings_show`, `settings_set` and `settings_reset`, as `settings` does; `accounts_status`, whether an account is linked on each site, and its level, never whose it is or its key; and `diagnostics`.

The server's instructions tell the agent which sites there are, `nexus`, `gamebanana`, `modio` and `degmods`, that every result names its site, how each names its games, and to search each site a game is on, since the same game on two sites is two games.

## Renamed arguments, limits and logs

An argument renamed in a release still works until the next major version. A call that uses it gets a `deprecated` block in its result (a code such as `DL_LINK_ARG`, the old argument, the one to use, the version that removes it, and an example with the call's own values), a note at the start of its message, a warning in the log, and a count in `deprecated-calls.json` beside `settings.json`, which `diagnostics` reports. Its description starts with "Deprecated", and its input schema marks it `deprecated`. A call whose arguments don't fit the tool, such as from an agent's app whose list of the tools is older than the server, fails saying what the tool takes; restarting the agent's app and starting a new conversation reads the tools again. It can't link accounts, delete the library's files, move the library, or take a site's links: those stay yours, in the desktop app or the command line. While the desktop app runs, the server asks it to download and change the downloads; otherwise it runs the downloads itself until none is under way, and closing it pauses what's left, which goes on the next time ModShelf runs the downloads. With a free Nexus Mods account, each download waits for you to start it on the website: `download` gives the page, and the desktop app, which the website's link starts, carries it on. The library keeps a year of what happened to its files, from 0.9.3 on: a file downloaded before then, or found by a rescan, says nothing of what it replaced, and `library_changes` reads the newest 1,000 events. The server logs to `cli-….log` with the command line, and never logs links. On Windows, **Restart to update** also ends a server started from the installed app; restart the agent's app to start it again.
