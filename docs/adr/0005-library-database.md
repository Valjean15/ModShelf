# 5. Library database on SQLite with EF Core

- Status: Accepted
- Date: 2026-10-23

## Context

Download jobs must survive restarts, so that a download paused or interrupted in one run continues in the next. The plan chooses SQLite through EF Core 10: a single-file library database with migrations. The download scheduler (ADR 0003) is the only writer, and it calls the repository from its single loop. `DownloadJob` is a state machine with private setters, and its value objects validate in their constructors, so EF Core can't build them without help.

## Decision

`AddLibraryDatabase(databasePath)` in `ModShelf.Infrastructure` registers an `IDbContextFactory<ModShelfDbContext>`, `DownloadJobRepository` as the `IDownloadJobRepository`, and a hosted service that migrates the database. The path must be absolute; the hosts choose it. The connection string is built with `SqliteConnectionStringBuilder`, so paths with spaces or semicolons are safe.

- **Each repository call uses its own short-lived context.** No tracked entity outlives a call, so the scheduler's long-lived `DownloadJob` objects never meet EF Core's change tracker.
- **A row class is mapped, not the domain entity.** The internal `DownloadJobRecord` has one column per value. Loading goes through `DownloadJob.Restore`, which applies the same checks as `Create` plus the state rules: status and reason are known values, only a Failed job has a reason, and the byte count lies within the file. A row that breaks them stops the load with an `InvalidDataException` naming the job, rather than dropping the job silently. Mapping `DownloadJob` directly was rejected because it needs private parameterless constructors on the entity and every value object, shaping the domain around EF Core.
- **One table, `DownloadJobs`:**
  - `Sequence` is an autoincrement integer key in insertion order. "Oldest first" is a plain `ORDER BY Sequence`, and jobs created in the same instant keep their order. SQLite can't sort `DateTimeOffset` values in SQL in any case.
  - `Id` is the job's GUID, with a unique index; updates find the row by it.
  - The file reference is four text columns: `SourceId`, `GameKey`, `ModId` and `FileId`.
  - `TargetDirectory`, `FileName`, and `CreatedAt`, which is stored as ISO 8601 text with its offset, at full precision.
  - `Status` and `FailureReason` are the enums' numbers, which the domain promises never to renumber. `BytesDownloaded` and `TotalBytes` are integers.
- **Updates write only what changes.** One `UPDATE … WHERE Id = @id` sets the status, byte count, size and reason. Updating a job that was never added throws.
- **The schema is migrated at startup.** `LibraryDatabaseMigrator` is an `IHostedLifecycleService`. Its `StartingAsync`, which the host runs before any hosted service's `StartAsync`, creates the folder and applies pending migrations, so the scheduler always finds the schema ready, whatever the registration order.
- **Migrations are generated by the dotnet-ef tool**, pinned in `.config/dotnet-tools.json`. Infrastructure references the EF Core Design package as a private, build-time-only dependency, and a design-time factory lets the tool build the model without a host. Migrations live in `src/ModShelf.Infrastructure/Persistence/Migrations` and are never edited once committed. A test fails when the model changes without a new migration.

Secrets never go in this database; they belong in the OS secret store.

## Consequences

- Changing the schema means changing the record or its configuration, then running `dotnet tool restore` (once) and `dotnet ef migrations add <Name> --project src/ModShelf.Infrastructure`, and committing the generated files. New migrations land next to the existing snapshot.
- Progress is saved only with status changes (ADR 0003), so after a crash the stored byte count can lag behind the `.part` file. That's harmless: a resumed transfer starts from the `.part` file's length (ADR 0004), not from the stored count.
- Pooled SQLite connections keep the file open while the app runs. Tests clear the pools before deleting their temp folders, because Windows won't delete an open file.
- A corrupt row blocks startup with a clear error instead of losing a job without a trace. If that happens in practice, a repair step can come later.
- Tests run against real SQLite files in temp folders, never an in-memory substitute, so they cover the SQL that ships.
