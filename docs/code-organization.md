# Code organization

Where files, types and members go. The rules apply to every project under `src` and `tests`. When a new kind of file doesn't fit, extend this document in the same change rather than inventing a one-off place.

## 1. Folders follow features

- Each project is split into **feature folders named after the domain concept**: `Accounts`, `Catalog`, `Downloads`, `Mods`, `Search`, `Sources`, `Links`, and later `Library` and `Updates`. Use the same names in every layer, so one feature can be followed from Domain to Desktop.
- Group by concept, not by kind. `DownloadJob`, its `DownloadJobId`, `DownloadJobStatus` and `DownloadFailureReason` sit together in `Downloads/`, not in `Entities/`, `ValueObjects/` and `Enums/`.
- **The namespace always matches the folder.** The build fails otherwise (IDE0130).

## 2. The project root

The root of a project holds only:

- its central contract, such as `IModSource` in Sources.Abstractions;
- its DI registration, `<Name>ServiceCollectionExtensions`, named after the last part of the project name (`ApplicationServiceCollectionExtensions`, `DirectUrlServiceCollectionExtensions`);
- in a source project, the `<Name>Source` class and the `<Name>Options` its registration takes (`NexusSource`, `NexusOptions`);
- in the two hosts, `Program` (and `App` in Desktop).

Everything else goes in a folder.

## 3. Role folders inside a feature

Split a feature folder by role only where the roles below apply. Don't add role folders anywhere else.

| Project | Folder | What goes there |
|---|---|---|
| Application | `<Feature>/` | What Application offers other layers: service interfaces (`IDownloadService`, `IAccountService`), their implementations, the models and exceptions they use. |
| Application | `<Feature>/Ports/` | Interfaces other projects implement for Application, and the types those interfaces exchange (`IFileTransfer`, `TransferOutcome`, `ISecretStore`, repositories, `IAuthPrompt`). |
| Infrastructure | `Persistence/` | The `DbContext`, its design-time factory, and database location, options and migration at startup. |
| Infrastructure | `Persistence/Tables/` | One row class per table, `<Entity>Record`, next to its EF configuration, `<Entity>RecordConfiguration`. |
| Infrastructure | `Persistence/Repositories/` | `<Entity>Repository`, implementing an Application port. |
| Infrastructure | `Persistence/Migrations/` | Generated by `dotnet ef`. Never edit a migration that's committed. |
| Platform | `<Feature>/` | One folder per OS service (`Secrets`, `OAuth`, `Browser`, later `Protocols`, `Notifications`). Per-OS implementations are named after their technology (`DpapiSecretStore`, `KeychainSecretStore`); a `<Library>Interop` class sits next to the class that calls it. |
| Presentation | `ViewModels/`, `Services/`, `Resources/` | ViewModels; navigation and dialog interfaces; `.resx` strings. |
| Sources.\<Name\> | root, then `<Capability>/`, `Api/` | `<Name>Source`, `Add<Name>Source()` and the `<Name>Options` it takes at the root; capability folders (`Accounts`, `Catalog`, `Downloads`) as the site grows; HTTP clients and DTOs in `Api/`. |
| Cli | `Commands/`, `Hosting/` | One `<Name>Command` per command with what only commands use (`ExitCodes`, output formatting); the host builder and lifetime. |
| Desktop | `Views/`, `Hosting/` | Windows and views (`.axaml` with code-behind); the host builder and lifetime. Later `Styles/` and `Services/` (Avalonia implementations of Presentation's services). |

## 4. Visibility

Other projects see a project only through what it makes public, so keep that to what they may use.

- **Behaviour is shared through interfaces, data through records.** Service interfaces and ports are public; the classes that implement them are `internal`.
- In Application, Infrastructure, Platform and every source, the only public types are:
  - interfaces and enums;
  - records: the data the interfaces exchange (`LinkedAccount`, `DownloadJobSnapshot`) and the options the `Add…()` methods take (`FileTransferOptions`);
  - exceptions callers catch (`UnsupportedLinkException`);
  - the `<Name>ServiceCollectionExtensions` class;
  - in a source project, its `<Name>Source` class, because the shared `SourceContractTests<T>` are typed by it;
  - EF Core migrations, which `dotnet ef` generates as public.

  An architecture test (`PublicSurfaceTests`) fails the build on anything else.
- **Hosts never name an implementation.** They call `Add…()` methods, which choose the class and its defaults: `AddLibraryDatabase()` picks the database location, and `AddDirectUrlSource()` plugs in a source.
- Domain and Sources.Abstractions are all contract, so their types are public. Presentation's ViewModels are public because Desktop's views bind to them.
- **Tests see internals.** `src/Directory.Build.props` lets each project's own test project, and only that one, see its internal types. Tests still use a class through its constructor and its public and internal members, never through reflection.

## 5. Helpers and extension methods

- A helper only one class needs stays a **private method** of that class.
- Shared by several classes in one feature, or naming a concept of the feature (such as the `.part` file of a download): an **internal class in that feature's folder** (`SecretNames`, `PartialFiles`).
- Shared by several features of a project: that project's **`Common/`** folder (`FileNames`, `WebUrls`).
- No `Helpers/`, `Utils/` or `Extensions/` folders.
- Extension methods follow the same rule, in a class named `<ExtendedType>Extensions`. DI registration is the exception: it sits at the project root (section 2).

## 6. Logging

- A class's log messages live in **`<Class>.Log.cs`**: the same partial class, with `[LoggerMessage]` methods named `Log<Event>`, called as `LogJobFailed(_logger, ...)`.
- No extension methods on `ILogger`: they would show up on every logger in the namespace.
- Each component area owns a block of 100 event IDs. Take the next free block for a new area, and add it here.

| Event IDs | Area |
|---|---|
| 1–99 | Application: download scheduler |
| 100–199 | Infrastructure: HTTP file transfer |
| 200–299 | Infrastructure: library database |
| 300–399 | Platform: secret stores |
| 400–499 | Application: accounts and credentials |
| 500–599 | Sources.Nexus |
| 600 onward | Next free block |

## 7. Files

- **One type per file**, internal types included, and the file is named after the type. Nested private types used only by their parent stay nested.
- Split a class into partial files named **`<Class>.<Topic>.cs`** when it passes about 400 lines or has a clearly separate part (`DownloadScheduler.Messages.cs`, `AccountService.Credentials.cs`). `<Class>.Log.cs` is always its own file.

## 8. Member order

Inside a type, top to bottom:

1. Constants, then static fields, then instance fields
2. Constructors
3. Events
4. Nested enums
5. Properties
6. Methods: public, internal, protected, private; within each, static before instance
7. Nested structs, then nested classes and records, last

Interface implementations and overrides follow the same order. Interop classes too: public declarations first.

## 9. Tests

- The settings every test project shares (xUnit v3 on Microsoft.Testing.Platform, one `xunit.runner.json`) live in `tests/Directory.Build.props`. A test project's file lists only its references and the shared helpers it links in.
- A test project mirrors the folders of the project it tests: tests for `src/X/Persistence/Repositories/DownloadJobRepository.cs` go in `tests/X.Tests/Persistence/Repositories/DownloadJobRepositoryTests.cs`.
- Test classes are named `<Class>Tests`, or `<Class><Aspect>Tests` when one class has several (`DownloadSchedulerLimitTests`).
- **`Fakes/`** holds only test doubles: classes that stand in for a production interface or class (`Fake…`, `InMemory…`, `Scripted…`, `Recording…`, `Controlled…`), plus the small types they record or return.
- Harnesses and builders used by one feature's tests sit next to those tests (`SchedulerHarness`, `TestLibraryDatabase`).
- Other helpers used across a test project go in its **`Common/`** folder. Shared sample values stay in `TestData.cs` at the project root.
- A source's recorded API responses live in its test project's **`Fixtures/Recorded/`**, next to the script that records them (`Fixtures/Record-NexusFixtures.ps1`). They're only ever re-recorded by that script, never edited by hand.
- Helpers used by more than one test project live once in **`tests/Shared`**, in the namespace `ModShelf.Testing`, and each project that needs them links the file in (`<Compile Include="..\Shared\TempFolder.cs" Link="Shared\TempFolder.cs" />`).
